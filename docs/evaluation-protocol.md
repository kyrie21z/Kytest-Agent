# 评测协议（冻结于运行任何实验之前）

本文件定义"我们的 Agent 生成的测试有多好"的**唯一判定口径**。

冻结的意义：这份协议在跑出任何结果之前写定。后续若发现口径有问题，
只能追加一节"协议修订"并说明影响，**不允许**悄悄改公式后再报告结果——
否则结论就变成"改 benchmark 迁就结果"，这正是开发计划里原则 A 要防的事。

---

## 1. 实验单位与范围

| 项 | 定义 |
|---|---|
| 实例来源 | HumanEval+（EvalPlus, NeurIPS 2023）固定子集，30 例，见 `benchmarks/DATASET.md` |
| 子集选择 | 按 `task_id` 数值排序后等距抽样，无随机数；由 `scripts/freeze_dataset.py` 可重现 |
| 被测系统（SUT） | 目标函数的参考实现（`solution.py`），即 HumanEval+ 的 `canonical_solution` |
| Agent 可见 | 工作区内的 `solution.py`（函数签名 + docstring + 参考实现） |
| Agent 不可见 | 官方测试、评测器、benchmark 目录、网络 |

**Agent 任务提示（冻结，所有变体完全一致）**：

```
Generate unit tests for solution.py in the current directory.
Write them to test_solution.py using pytest.
```

任务提示**只出现在 user message 里**。变体之间的差异只允许来自 system prompt、
工具集与编排策略。若某个变体改了任务提示，该变体不能与其它变体进入同一张主表。

## 2. 指标定义

### 2.1 主终点：变异杀伤率（mutation score）

\[
mutation\_score = \frac{|\{m : m \in M,\ tests\ fail\ on\ m\}|}{|M|}
\]

- \(M\) = 对 `solution.py` 施加单点变异得到的变异体集合，上限 20 个，
  按"行号 → 列号 → 算子类型 → 遍历索引"字典序确定性抽样（不用随机数，保证可复现）。
- 一个变异体被杀 \(\iff\) 用**Agent 生成的测试**运行它时，至少有一个测试失败
  （任意失败原因都算：AssertionError、异常、收集错误）。
- 变异体运行超时算**未杀死**——超时无法证明测试发现了这个变异。
- **Agent 没有产出测试文件时 \(mutation\_score = 0\)**。
  这不是"未测量"：该实例确实有变异体集合，而测试没杀死任何一个。

**零变异体实例的处理**。少数实例的参考实现里没有可变异算子（例如只做集合运算），
此时 \(mutation\_score\) 记为 **null（未采集）**，该实例**不进杀伤率的分母**，
但通过率与覆盖率仍然正常计入。理由是"无法测量"和"测得 0"是两件不同的事：
把前者记成 0 会系统性地拉低均值。`mutants_total = 0` 的实例数量必须在报告中列出。

选它作主终点的理由：它绕开了 Oracle 问题。我们不需要知道所有输入的正确答案，
只要测试能区分"原程序 vs 被改坏的程序"，就证明它具备故障检测能力。
覆盖率不具备这个性质——把所有代码调用一遍而不写有效断言，覆盖率可以很高。

**仪器校准结果**（`scripts/calibrate_instrument.py`，在跑任何实验之前执行）：

| 测试质量档位 | 覆盖率 | 杀伤率 |
|---|---:|---:|
| 官方测试 | 100% | **96.9%** |
| 单条弱断言 | 25–50% | 0.0% |
| 只调用不断言 | 25–50% | 0.0% |

两个方向都通过：官方测试得高分（说明引擎不会把好测试判死），空测试接近 0
（说明引擎不会把"什么都没测"判成"测得好"）。注意覆盖率在三个档位之间**无法区分**
弱断言与空测试——这正是必须用杀伤率作主终点的经验证据。

**主终点在阶段 4a/4b 的区别**：4a 只采集，4b 才用于对比。
若 4b 未实现，主表以 `pass_rate` + `line_coverage` 报告，并明确标注
"主终点未采集"，不得用其它指标冒充主终点。

### 2.2 有效性门槛：可通过性（pass rate）

\[
all\_pass = \mathbb{1}[\text{Agent 的测试在正确实现上全部通过且无收集错误}]
\]

- 它是**门槛指标，不是质量指标**：零断言测试也能 \(all\_pass = 1\)。
- \(all\_pass = 0\) 的实例仍然进入主表统计（见 §5 的 ITT 原则），
  不因为"测试自己有问题"就被剔除——那恰恰是要测量的现象。
- 同时记录 `import_ok`（测试文件能否被导入），用于区分"测试逻辑错"与"测试文件根本跑不起来"。

### 2.3 中介变量：覆盖率

\[
line\_coverage = \frac{\text{solution.py 中被执行的行数}}{\text{solution.py 的可执行行数}}
\]

- 用 `coverage.py`（`coverage run -m pytest` + `coverage json`）采集。
- 只统计 `solution.py` 一个文件。
- 测试文件存在但全部收集失败时，\(line\_coverage = 0\)。
- 覆盖率是**机制变量**而非终点：它回答"测试有没有执行到代码"，
  不回答"测试有没有能力发现错误"。二者的差异正是 RQ3 要问的。

### 2.4 成本指标

`turns`、`llm_calls`、`tool_calls`、`input_tokens`、`output_tokens`、`runtime_sec`
全部取自 `Agent` 的累计计数器（`RunResult`），不做事后估算。

## 3. 停止规则（冻结）

**所有变体使用同一个固定预算，且停止规则不引用任何被评测的指标。**

| 参数 | 值 |
|---|---|
| `max_turns` | 8 |
| checkpoint | 每完成第 1、2、4、8 个 turn 时记录一次指标 |
| 单次 Agent 运行的墙钟上限 | 300 秒，超时记为 `timeout` |

明确禁止的停止规则（写在这里是为了让"我们没这么做"可被核对）：

- ❌「跑到覆盖率不再增长为止」——停止规则由被评测指标定义，属于自证式选择效应；
- ❌「跑到测试全部通过为止」——同上，会让变体获得额外轮次。

质量–预算曲线的实现方式：用 `Agent.run_until(n)` 在 n = 1, 2, 4, 8 处挂起，
在工作区上采集指标后继续运行。这比"每个 checkpoint 重跑一遍"便宜一个数量级，
且状态连续。

## 4. 环境与隔离

| 项 | 要求 |
|---|---|
| Agent 工作区 | 临时目录，只含 `solution.py`；无 `.git`、无官方测试、无 benchmark 目录 |
| 评测器位置 | **工作区之外**（`eval/`，目录分离防止数据集与官方测试进入上下文）。注意这是目录级隔离而非权限隔离：`run_command` 的子进程拥有父进程的操作系统权限，可读写工作区外的文件；真正的访问控制依赖外部机制，见下条 |
| 网络 | 评测时视为不可用。若 Agent 尝试联网（`run_command` 中出现 curl/wget/pip install/git clone），记录 `network_attempt` 标志 |
| 命令执行 | 继承当前解释器环境；`PYTHONDONTWRITEBYTECODE=1` 保持工作区干净 |
| 环境快照 | 记录 python 版本、pytest 版本、coverage 版本、模型名与温度，写入结果文件 |
| 无关文件清理 | 评测前删除 Agent 工作区里的 `.sessions/` 等产物，避免影响覆盖率的可执行行数统计 |

**已知的隔离缺口（写入 Threats to Validity）**：`run_command` 是通用 shell，
能执行 `pip install evalplus` 之类的命令，且子进程可读写工作区外的文件
（目录分离不构成权限边界）。我们**不**通过封禁命令来防污染
（那会破坏 A0 的通用性），而是：(1) 在离线环境中运行实验；(2) 用
`network_attempt` 标志做统计上的事后核对——若某个变体的联网尝试比例异常，
该变体的结果需要单独说明。

## 5. 无效运行的计分（ITT 原则）

> **所有启动过的运行都进入统计。** 没有"这个实例不算"的白名单。

| 情况 | status | 主终点 | 覆盖率 | 计入分母 |
|---|---|---|---|---|
| Agent 未产出测试文件 | `no_tests` | 0 | 0 | ✅ |
| 测试文件存在但无法导入/收集 | `import_error` | 0 | 0 | ✅ |
| 测试能跑但有失败 | `partial_pass` | 按实际计算 | 按实际计算 | ✅ |
| 测试全部通过 | `all_pass` | 按实际计算 | 按实际计算 | ✅ |
| Agent 运行超时 | `timeout` | 0（除非超时前已写出测试文件） | 同上 | ✅ |
| LLM 调用失败 | `llm_error` | 0 | 0 | ✅ |
| 触达 turn 预算 | `max_turns` | 按实际计算 | 按实际计算 | ✅ |
| 评测器自身异常 | `eval_error` | 0 | 0 | ✅，并单独报告数量 |
| 实例准备失败（数据集损坏） | — | 不进入统计 | — | ❌，必须为 0 |

最后一行是唯一允许剔除的情况：实例本身无法准备。这类失败必须报告数量，
且正常应为 0——不为 0 说明数据集或工作区准备有 bug，要先修工具再跑实验。

## 6. 统计分析计划（预注册）

| 项 | 做法 |
|---|---|
| 主比较 | 配对差值：同一实例上 variant B − variant A |
| 效应量 | 均值差 + 95% bootstrap 置信区间（10000 次重采样，固定 seed） |
| 显著性 | Wilcoxon signed-rank（配对、非参数、n=30 时比 t 检验稳健） |
| 多重比较 | 3 个主比较（A0→A1、A1→A2、A2→A3）用 Holm 校正 |
| 方差 | 每个变体在**同一批实例**上运行，实例内方差由 checkpoint 曲线提供 |
| 报告原则 | 报效应量与置信区间，不只报均值；不显著就说"未检测到差异" |

**样本量的诚实说明**：n = 30 的配对设计约能检出 0.5 个标准差的效应
（α=0.05, power=0.8）。小于该量级的差异检测不出来——这不是缺陷，
而是必须在报告里写明的分辨率上限。要检出更小的效应需要更多实例，
而那是时间预算不允许的。
