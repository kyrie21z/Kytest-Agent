# Design：可运行、可验证的代码助手

## 1. 从作业目标确定边界

作业要求一个简单Agent、至少一种真实工具和CLI/Web入口。项目选择CLI和
Python测试生成；评审应能看到源码被读取、测试被写入、执行结果影响后续动作。
因此主要交付是一个可运行的工具闭环，实验用于检验设计取舍。

测试有两条独立要求：在参考实现上可运行，以及能用有效断言区分错误行为。
恒真断言可能通过，错误断言可能对所有程序都失败，两者都不能证明判别力。

## 2. 组件与流程

| 组件 | 职责 | 入口 |
|---|---|---|
| CLI | 配置、连续任务、文本/JSON输出 | `src/code_agent/cli.py` |
| Agent | 唯一的LLM与工具循环，步骤与上下文控制 | `src/code_agent/agent/core.py` |
| LLM适配 | OpenAI兼容API、工具调用解析、超时与重试 | `src/code_agent/llm.py` |
| 工具 | 文件读取/写入/搜索、受限命令执行 | `src/code_agent/tools/` |
| 测试生成 | 契约检查、逐条验证、接受集合与开发反馈 | `testgen.py`、`test_contracts.py`、`fault_feedback.py` |
| 评测 | 在生成结束后独立执行参考及固定故障池 | `eval/` |

每次turn调用一次LLM，再执行该响应中的工具调用。工具结果写入对话，下一次
请求据此修正或结束。无工具的最终回答、步骤/token边界、外部失败或停止钩子
均能结束任务。核心通过事件输出状态，CLI和评测订阅同一核心，不解析终端文本。

Web入口`web.py`由标准库HTTP服务提供，复用CLI的`build_agent`工厂和事件接口。
浏览器轮询事件，不调用模型服务；真实模型缺少配置时明确拒绝，离线示例单独标注。
每次运行有独立临时工作区，最后再执行一次可见的pytest复验；前后检查目标源码，
改写则恢复并判为无效。停止在请求/工具边界生效，最近8份运行保留到服务结束。
对比入口冻结同一源码、任务和配置，依次运行A0/A4；等候时间不计入A4执行耗时。
候选依据与状态直接来自实际提交事件和工具报告，展示过程约束，不推断质量优势。

## 3. 接口与权限

模型响应是文本与结构化工具调用；工具提供JSON Schema及`run()`接口。
参数缺失、类型错误、未知工具和执行失败转成错误观察。上下文按assistant/tool
消息组裁剪，避免孤立的工具返回破坏API消息顺序。会话轨迹保存事件并脱敏密钥。

文件工具限制工作区路径、符号链接和文件大小。命令不经过shell，带超时及输出
边界；默认Bubblewrap只挂载工作区和只读运行库，隔离网络并过滤子进程环境。
隔离不可用时拒绝执行；`trusted`是具有宿主权限的显式受信模式。只读与禁用
策略分别限制写入和执行，不能靠换工具绕过。

## 4. 测试生成机制

默认A0只用通用工具，仍可以自行运行pytest。A4通过`submit_tests`接收候选，
要求契约引用、输入域、独立预期值及故障假设；有限结构检查识别可解析的域约束、
无关断言、自比较及代数消去型弱锚点。动态调用在隔离子进程记录实际参数。

每条候选最多2秒，合并回归最多5秒；每批最多6条、每run最多24次候选尝试，
每项测试最多128次目标调用。失败候选不覆盖已接受集合，已有测试保留为基底，
目标源码被恢复。未知约束明确标为未检查，不认证复杂oracle或全域正确性。

A5在接受套件后自动检查最多8个AOR/CRP开发故障，最多两轮改变套件的反馈。
有剩余目标时要求追加测试，目标耗尽、预算耗尽或无进展时停止。相同套件复用
缓存。最终独立评分使用ROR/LCR/BCR，两池按AST指纹核对无交集；评分结果
不反馈给模型。开发目标耗尽不代表独立质量达标。

## 5. 验证与取舍

核心回归覆盖模型解析、消息序列、工具参数、路径/权限、进程超时、错误传播、
候选拒绝与保留、有效测量及反馈闭环。离线演示使用脚本化模型和真实工具，
证明控制流程可运行；真实模型效果另用保存的实验记录判断。

[EXPERIMENTS.md](EXPERIMENTS.md)分别报告100份HumanEval结果与180份MBPP重复
结果，保留失败分母，不合并版本或评分池。最新A4/A5约+6.1个百分点的观察
增益未通过统计验收，默认仍是A0；A5有一个独立增量例，但没有平均质量优势证据。

已知限制：公开基准的预训练接触未知；疑似等价故障与超时不能当确认检出；
参考实现不一定全域正确，最新重放的一份随机排序测试已暴露该问题；软预算
不能保证严格成本相等。不存在对任意真实仓库缺陷迁移或质量等价的承诺。

## 6. 为什么精简提交

评分所需的最小证据是：代码可运行、工具闭环真实、关键行为有回归、结论可核对。
所以提交入口仅为README、本文和实验摘要；白名单打包排除调参轮、批量工作区、
完整请求档案和重复源码快照，保留280行带原件哈希的派生记录及一份真实轨迹。
完整档案仍在精简前Git版本中，源代码与历史实验没有因精简而删除。

提交中的回归子集保持原测试字节；一个冻结变异器文件与两份小数据集只为
现有测试提供fixture，不是新增实验。源码保持精简前的已验证实现。
